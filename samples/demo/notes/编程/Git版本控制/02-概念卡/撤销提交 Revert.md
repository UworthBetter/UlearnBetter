# 撤销提交 Revert

> [!abstract] 一句话定义
> ==生成一个反向提交把代码退回过去，原历史保留，是已推送提交上最安全的撤销方式。==

## 📌 是什么

- `git revert` 的作用类似“撤销（undo）”：选中某一笔提交，把代码退回到它之前的状态，但==不删除原提交==，而是新建一笔反向提交来抵消它（[2:21](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=141s)，秒数以视频为准）
- 与 `--amend` 的适用场景正好互补：amend 适合还没推送的最近一次提交；一旦代码已经推到远程仓库，就应改用 revert 来撤销（[2:00](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=120s)）
- 因为它不重写历史，所以不会像 `git push --force` 那样覆盖远程提交、让协作者的提交丢失——作者原话提醒强推会让“co-workers 可能不太高兴”（[2:00](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=120s)）
- 视频里的比喻：revert 比事后像“创伤外科医生”一样把东西拼回去要容易得多（[2:42](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=162s)，以视频为准）

## 🧩 在视频/系统中的角色

出自 **ch07 修补与撤销提交**。这一章讲“快出了错怎么办”：先用 `--amend` 修补未推送的最近提交，revert 则承担“已推送代码的后悔药”这一职责——在不破坏共享历史的前提下安全地回退某笔提交。

## 📌 执行顺序

1. 确认要撤销的那笔提交已经推送到远程（或任何不便改写历史的场合）
2. 运行 `git revert <提交>`（具体命令参数以视频为准）
3. Git 自动生成一笔反向提交，代码回到目标提交之前的状态
4. 正常 `git push` 推送即可，无需强推

## ⚖️ 优点与局限

| ✅ 优点 | ⚠️ 局限 |
| --- | --- |
| 原提交保留在历史中，不重写历史，对已推送/共享分支安全 | 撤销操作本身会多出一笔提交，历史不如 amend 干净（以视频为准） |
| 不需要 `git push --force`，不会覆盖远程、不会丢掉协作者的提交 | 只能“回退到之前的状态”；若想彻底抹除痕迹，revert 做不到（以视频为准） |
