# 二分排查 Bisect

> [!abstract] 一句话定义
> ==在已知好与坏的两个提交之间做二分搜索，快速定位引入 bug 的那一笔。==

## 📌 是什么

- 当项目越来越复杂，`git log` 的输出越来越难读，而其中很可能藏着某笔正在让应用出问题的提交（[4:48](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=288s)）。
- `git bisect` 让你从一个已知有 bug 的提交出发（通常是最近的提交），再指定一个你确定应用还能正常工作的提交（比如几小时前的某笔）作为“好”的边界。
- 指定两端之后，Git 会在好与坏之间执行二分搜索（binary search），逐笔带你检查中间的提交。
- 每到一个检查点，如果该提交看起来正常，就输入 `bisect good` 跳到下一笔；持续标注，直到锁定那笔坏提交。
- 最终你能精确找到出问题的提交，从而知道到底哪段代码需要修复（[5:09](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=309s)）。

## 🧩 在视频/系统中的角色

出现在 **ch09 日志美化与历史排查** 一章，与 `git log` 美化输出放在一起，属于“历史排查”工具箱的一员：日志美化帮你读懂历史，Bisect 则帮你在历史中快速定位引入 bug 的那笔提交，是工作流提效手段之一（作者称之为“每个开发者都该掌握的进阶 Git 技巧”）。

## 📌 执行顺序

1. 确认当前有一笔已知有 bug 的提交（通常是最新提交），以它为起点启动 `git bisect`。
2. 指定最后一个你确定应用正常工作的提交作为“好”的边界。
3. Git 在两笔提交之间做二分搜索，把你带到中间的某个提交。
4. 检查该提交：如果没问题，输入 `bisect good`，Git 继续走查下一笔。
5. 重复标注，直到最终锁定那笔坏提交，明确知道哪段代码需要修复。

## ⚖️ 优点与局限

| ✅ 优点 | ⚠️ 局限 |
| --- | --- |
| 用二分搜索逐段缩小范围，比逐笔人工翻查历史快得多 | 需要你先知道（或能找到）一笔“好”的提交作为边界 |
| 最终能精确指出引入 bug 的提交，明确该修哪段代码 | 每个中间检查点都需要你手动判断提交是好是坏（以视频为准） |
| 是作者强调“每个开发者都该掌握”的进阶排查技巧 | 前提是 bug 确实是由某笔提交引入的，其他成因需另行排查（以视频为准） |
