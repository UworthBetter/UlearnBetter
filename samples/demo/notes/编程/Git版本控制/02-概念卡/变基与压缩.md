# 变基与压缩

> [!abstract] 一句话定义
> ==用交互式 rebase 的 squash 或 fixup 把零散提交整理压缩成一个干净的提交。==

## 📌 是什么

- 常见场景：在特性分支上积累了多个提交（如三个），提交信息大多没有意义，合并进 main 之前最好压缩成一个干净的提交，让历史更易读（[5:09](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=309s)）。
- 核心命令是在特性分支上运行 `git rebase` 并带上交互选项（interactive），目标分支为 main：`git rebase -i main`（[5:30](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=330s)）。
- 执行后 Git 会打开一个文件，列出该分支上的所有提交；可用 `pick` 保留提交、`reword` 修改提交信息、`squash` 把提交合并进原始提交（[5:30](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=330s)）。
- 保存关闭文件后，Git 会再打开一个文件让你更新合并后的提交信息，默认内容是所有被压缩提交信息的组合；如果不想保留这些信息，可用 `fixup` 代替 `squash`（[5:51](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=351s)）。
- 提效技巧：提交时就用 `--fixup` / `--squash` 标志，提前告诉 Git 这笔提交将来要被压缩；之后 rebase 时配合 `--autosquash` 标志即可自动完成压缩（[6:12](https://www.youtube.com/watch?v=ecK3EnyGD8o&t=372s)）。

## 📌 执行顺序

1. 在特性分支上运行交互式 rebase，指向 main 分支（如 `git rebase -i main`）。
2. 在弹出的文件中，用 `pick` 保留要用的提交，用 `reword` 改信息，用 `squash` 把后续提交合并进第一个提交。
3. 保存并关闭文件。
4. Git 弹出第二个文件，编辑合并后的提交信息（默认是所有被 squash 提交信息的组合；若用 `fixup` 则跳过合并信息）。
5. （提效做法）平时提交时用 `--fixup` / `--squash` 标记，之后 rebase 加 `--autosquash` 自动完成压缩。

## ⚖️ 优点与局限

| ✅ 优点 | ⚠️ 局限 |
| --- | --- |
| 把一堆无意义的零散提交合并成一个干净提交，历史更易读 | 交互式 rebase 改写提交历史，操作步骤较多、需谨慎 |
| `fixup` 不保留被压缩提交的信息，省去编辑合并信息的麻烦 | 平时就要有意识地用 `--fixup`/`--squash` 提交，事后补救则需手动整理 |
| 配合 `--autosquash` 可自动完成压缩，非常高效 | 已推送到共享分支的提交是否适合变基，视频未展开，以视频为准 |
