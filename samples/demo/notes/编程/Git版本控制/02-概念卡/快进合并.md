# 快进合并

> [!abstract] 一句话定义
> ==当目标分支没有新提交时，合并只是把指针直接前移到特性分支的最新提交，不产生新的合并提交。==

## 📌 是什么

- Git 的一种合并方式：目标分支（如 master）自分叉后没有任何新提交时，Git 无需真正“合并”，只需把分支指针直接移到特性分支的最新提交即可。
- 视频中的典型场景：从最新提交创建新分支（如 `git checkout -b feature`），在新分支上修 bug 或开发新功能并提交，然后切回 master 合并回来——由于 master 期间没有新提交，这次合并就是快进合并（[4:53](https://www.youtube.com/watch?v=HkdAHXoRtos&t=293s)、[5:34](https://www.youtube.com/watch?v=HkdAHXoRtos&t=334s)）。
- 这种分支 + 合回的工作流让多个开发者可以在各自的分支上工作而不互相干扰（[5:14](https://www.youtube.com/watch?v=HkdAHXoRtos&t=314s)）。
- 快进合并意味着提交历史是线性的，不会出现“合并提交”（merge commit）；若 master 有新提交则不能快进，可能产生冲突——参见 [[合并冲突]]。

## 🧩 在视频/系统中的角色

出现在 [[ch03 分支与快进合并]]，是视频“分支与合并”这一主题的核心机制：它解释了从特性分支把成果带回主线时，Git 最简单、最干净的合并形态，与后续章节涉及的 [[合并冲突]]、[[变基与压缩]] 等复杂情形形成对照。

## 📌 执行顺序

1. 基于最新提交创建并切换到新分支：`git checkout -b feature`（[5:34](https://www.youtube.com/watch?v=HkdAHXoRtos&t=334s)）。
2. 在特性分支上开发，把改动暂存并提交到该分支（[5:34](https://www.youtube.com/watch?v=HkdAHXoRtos&t=334s)、[5:55](https://www.youtube.com/watch?v=HkdAHXoRtos&t=355s)）。
3. 切回 master：`git checkout master`，此时特性分支上的新文件会消失、回到 master 原状（[5:55](https://www.youtube.com/watch?v=HkdAHXoRtos&t=355s)）。
4. 在 master 上合并特性分支；因为 master 没有新提交，Git 直接快进指针到特性分支的最新提交。
5. （若改动只完成一半不想提交，可先用 git stash 收起，切回后再取回，详见 [[贮藏 Stash]]。）

## ⚖️ 优点与局限

| ✅ 优点 | ⚠️ 局限 |
| --- | --- |
| 不产生多余的合并提交，历史保持线性、干净 | 仅当目标分支没有新提交时才可能；一旦双方都有新提交就无法快进 |
| 合并过程零风险，不会触发人工解决冲突的步骤 | 若目标分支已前进，合并可能遇到 [[合并冲突]]，需人工裁决（以视频为准） |
| 特性分支上的开发被完全隔离，多人协作互不干扰（[5:14](https://www.youtube.com/watch?v=HkdAHXoRtos&t=314s)） | 线性历史会丢失“这批提交来自哪个特性分支”的信息，是否需要保留需结合团队习惯（以视频为准） |
