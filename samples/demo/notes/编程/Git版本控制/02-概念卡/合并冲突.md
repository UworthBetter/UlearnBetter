# 合并冲突

> [!abstract] 一句话定义
> ==两条分支改动了同一处代码，Git 无法自动裁决，需要人工选择保留哪一边。==

## 📌 是什么

- 多数情况下合并能自动完成，但==合并是最容易出问题的地方==：当你开发分支时，master 分支也发生了改动，两边改到同一行代码，就会产生冲突。[视频 6:58](https://www.youtube.com/watch?v=HkdAHXoRtos&t=418s)
- 冲突的本质是 Git “开箱即用”时无法判断该用哪边的变化，因此不会自动合并这些文件。[视频 7:20](https://www.youtube.com/watch?v=HkdAHXoRtos&t=440s)
- 编辑器（如 VS Code）会给出解决选项：接受当前改动（accept current change）、接受传入的改动（accept incoming change）或两者都保留。[视频 7:20](https://www.youtube.com/watch?v=HkdAHXoRtos&t=440s)
- 作者建议：遇到冲突时先仔细审阅，很多时候==直接中止合并（abort the merge）、手动修复文件==反而更稳妥。[视频 7:20](https://www.youtube.com/watch?v=HkdAHXoRtos&t=440s)
- 做大量小提交是缓解冲突的好习惯——修一个文件的冲突，远比修一百个文件的冲突容易。[视频 7:40](https://www.youtube.com/watch?v=HkdAHXoRtos&t=460s)

## 🧩 在视频/系统中的角色

出现在 ch04《Stash 与合并策略》。视频先演示了顺利的合并场景（[[快进合并]]），随后指出合并是冲突高发地，并用“feature 分支与 master 分支改了同一行代码”的例子讲解冲突的产生、解决选项与规避策略。它也是视频中“多用小提交”这一建议的主要理由。

## 📌 执行顺序

1. 运行合并时遇到冲突，先 ==审阅冲突内容==，看清两边各改了什么。[视频 7:20](https://www.youtube.com/watch?v=HkdAHXoRtos&t=440s)
2. 借助编辑器提供的选项处理：接受当前改动 / 接受传入改动 / 两者都保留。
3. 冲突复杂时，考虑直接 ==中止合并（abort the merge）==，改为手动修复文件。[视频 7:20](https://www.youtube.com/watch?v=HkdAHXoRtos&t=440s)
4. 长期开发分支时，==定期把 master 合并回自己的分支==（master 有变化就合，活跃仓库可每天一次），尽早暴露冲突。[视频 8:02](https://www.youtube.com/watch?v=HkdAHXoRtos&t=482s)
5. 日常坚持小步提交，缩小未来冲突的修复面。

## ⚖️ 优点与局限

| ✅ 优点 | ⚠️ 局限 |
| --- | --- |
| 冲突机制保住了两边的改动都不会被悄悄覆盖，强迫开发者做出明确选择 | Git 无法自动裁决同处改动，“开箱即用”时无法直接合并这些文件 |
| 冲突通常只发生在少数文件，配合小提交习惯可以快速修复 | 冲突文件一多，人工逐个修复成本很高；作者建议复杂时中止合并手动处理 |
