# ch03 分支与快进合并

> [!info] 视频位置
> [4:52 Branch](https://www.youtube.com/watch?v=HkdAHXoRtos&t=292s) · [5:39 Fast Forward](https://www.youtube.com/watch?v=HkdAHXoRtos&t=339s)

## 🎯 本章目标

能基于最近的提交创建并切换分支，把新代码的开发隔离在独立分支上，并理解快进（Fast Forward）合并发生的条件。

## 分支：为什么需要它

视频把 master 分支比作树的主干（[4:53](https://www.youtube.com/watch?v=HkdAHXoRtos&t=293s)）——它承载实际要发布给客户的源代码。当你有一个稳定的代码库，又需要修 bug 或试验新功能时，典型做法是：

- 基于最近一次提交创建一个新分支；
- 在这个独立分支上修 bug、写功能；
- 完成后再合并回 master。

这样做意味着多个开发者可以在各自的分支上同时工作，互不干扰、互不“踩脚”（[5:14](https://www.youtube.com/watch?v=HkdAHXoRtos&t=314s)）。

## 创建与切换分支步骤

视频演示的完整流程如下：

1. 运行 `git branch` 查看当前所有分支（此时只有 master）。
2. 用 `git checkout` 加 `-b` 标志创建并切换到新分支（视频里命名为 `feature`）——分支尚不存在时必须带 `-b`。
3. 在 feature 分支上写代码，所有改动都被隔离在这个分支内。
4. 把新代码提交到 feature 分支（视频中直接在 VS Code 里执行提交）。
5. 切换回 master 分支——此时 feature 分支上新增的文件会“消失”，master 回到原始状态（[5:55](https://www.youtube.com/watch?v=HkdAHXoRtos&t=355s)）。
6. 之后即可快进（fast forward）合并 feature 分支的内容。

> [!tip] 切换分支前必须提交吗？
> 不一定。视频提到，如果你有写到一半的、实验性的工作，可以先不提交，改用 `git stash` 把进行中的工作暂存起来再切换分支——这部分在 [[ch04 Stash 与合并策略]] 展开（[6:15](https://www.youtube.com/watch?v=HkdAHXoRtos&t=375s)）。

## 快进合并

视频在 Fast Forward 一节演示了快进场景：feature 分支基于 master 的最新提交创建，master 在此期间没有新提交。此时合并 feature 分支，Git 只需要把 master 的指针“快进”到 feature 的最新提交即可，不会产生合并提交。

理解要点（结合视频演示归纳）：

- **发生条件**：master 在分支创建后没有自己的新提交，分支的提交历史是 master 历史的直接延伸。
- **若条件不满足**：两条分支各有独立提交，快进无法进行，需要走真正的合并流程（见 [[ch04 Stash 与合并策略]]）。
